# Interview Preparation — SigmaForge (Project-Wide)

30 technical questions spanning the whole project, with answers grounded
in what's actually built (v0.1.0 / E0) versus designed. For auth-specific
deep-dive questions, see `docs/subsystems/auth/INTERVIEW_PREP.md` — this
document is broader and less redundant with that one.

## Architecture & Design

**1. Walk me through the overall architecture.**
Monorepo: FastAPI backend, Celery worker, React/TypeScript frontend,
PostgreSQL, orchestrated with Docker Compose. See
`docs/ARCHITECTURE_WALKTHROUGH.md` for a full request-by-request trace
with diagrams. Today, only the auth slice and health checks are wired
end-to-end; the schema and infra support the full target platform.
*Follow-up: "What's actually running today vs. designed?"* — auth, RBAC,
health checks, one worker task, one frontend page. Everything else in
`docs/ARCHITECTURE.md` is designed, not built.

**2. Why a monorepo instead of separate repos per service?**
At this stage, a single engineer (or small team) benefits more from
atomic cross-cutting changes (e.g., a schema change touching backend and
a future frontend type) and one CI pipeline than from the deploy
independence separate repos would buy. `docs/REPO_STRUCTURE.md` documents
this as a stage-appropriate choice, not a permanent architectural stance.

**3. Why the repository pattern for the auth domain?**
Business logic (`AuthService`) depends only on `Protocol` interfaces, not
directly on SQLAlchemy. Production code gets a real SQLAlchemy
implementation; tests get an in-memory fake. This means 11 of the 20
backend tests run without a database at all, in under a second, while
still exercising the exact class production traffic uses.
*Follow-up: "Isn't that over-engineering for one domain?"* — Fair
pushback. It's justified here because auth is the first subsystem and
sets the pattern every later domain (rules, SIEM integrations) will
follow; paying the abstraction cost once, early, is cheaper than
retrofitting it after three domains exist without it.

**4. Why declarative RBAC instead of role checks in each route?**
`ROLE_PERMISSIONS: dict[str, set[str]]` plus one `require_permission()`
dependency is the single source of truth, diffable against the documented
authorization matrix. No route branches on `role.name` directly, so the
permission matrix can't silently drift from what the code enforces in more
than one place.

**5. Why does the database schema include 20 tables when only 5 are used
today?**
The migration was written for the full target platform in one pass
(hand-written DDL, validated against the real PostgreSQL grammar via
`pglast`, not autogenerated), rather than incrementally adding tables per
milestone. That's a deliberate trade-off: it front-loads schema design
work but means later milestones (E1's `detection_rules`, R1's
`experiment_runs`) never need a schema migration that risks breaking
existing data. The cost is that `docs/DATABASE_SCHEMA.md` needed an
explicit "what's actually used today" callout so it doesn't read as
overclaiming.

**6. What would you change about the architecture if you were starting
over?**
Honestly, probably nothing structural yet — it's early enough that the
repository pattern, declarative RBAC, and shared production/research
schema have all paid off without yet showing their costs. The thing I'd
watch is whether the "one big migration up front" choice from Q5 becomes
painful once real schema evolution is needed against non-empty tables;
that's untested territory.

## Security

**7. Why RS256 instead of HS256 for JWTs?**
Asymmetric signing separates the signing key (private, API-only) from the
verification key (public, shareable). Today, with one monolithic service,
the practical difference is small; the value is that a future service
that only needs to verify tokens never needs the private key, avoiding a
signing-scheme migration later.

**8. How do you prevent account enumeration?**
Every login failure path — nonexistent user, wrong password, locked
account — returns the identical generic error. For a nonexistent user,
`verify_password()` still runs against a precomputed real Argon2 hash (not
a fake-looking string) so the response-time shape matches a real failed
check. *Follow-up: "Have you measured that the timing actually matches?"*
— No, and I say so directly in `docs/subsystems/auth/SECURITY_ANALYSIS.md`
— the mitigation is implemented correctly but not statistically verified
under load. That's a named gap, not a hidden one.

**9. Explain the refresh token rotation and reuse-detection design.**
Refresh tokens are single-use: presenting one revokes it and issues a new
one (rotation). Presenting an already-revoked token is treated as evidence
of theft — two parties holding what should be a single-use secret — and
the service revokes every active refresh token for that user. Detection
window is one refresh cycle; it doesn't prevent the first fraudulent use.

**10. Why hash refresh tokens with SHA-256 but passwords with Argon2id
— isn't that inconsistent?**
No — different threat models. Passwords are low-entropy, human-chosen, and
need to resist offline dictionary/brute-force attacks (Argon2id is
deliberately slow and memory-hard for exactly that). Refresh tokens are
high-entropy random values with no dictionary to brute-force against; a
fast hash adds no security value there and would add unnecessary latency
to every authenticated request.

**11. What's your threat model for the research subsystem specifically?**
`docs/THREAT_MODEL.md` §7 covers dual-use content handling (the attack
corpus is deliberately adversarial data), a researcher-self-approval
conflict (a researcher generating experiment rules cannot also approve or
deploy them, even experiment-generated ones — enforced by RBAC, not just
policy), and an evaluation-awareness confound (if a model can tell it's
being tested, that changes its behavior in ways that could invalidate
results). None of this subsystem is built yet; the threat model was
written before the code specifically so these controls get designed in,
not retrofitted.

**12. What security work is explicitly not done yet?**
Multi-factor authentication, password reset/email verification, rate
limiting at the IP/network level (account lockout only protects a single
account), and a full automated RBAC-matrix regression test. All named
directly in `docs/subsystems/auth/FUTURE_WORK.md`, not glossed over.

**13. How would a compromised database affect this system?**
Passwords are Argon2id-hashed (resistant to offline cracking). Refresh
tokens are SHA-256-hashed with no raw value stored, so a dump alone
doesn't yield usable tokens. JWT signing keys are not in the database (env
vars / secrets manager). What a DB compromise *would* expose: user emails,
roles, and metadata — not directly exploitable credentials.

**14. What's the single security decision you're least confident about?**
Deferring access-token instant revocation (no denylist — a deactivated
user's still-unexpired JWT is cryptographically valid for up to 15
minutes, though `is_active` is re-checked from the database on every
request so *authorization* effectively updates immediately even if the
token itself doesn't expire early). It's a documented trade-off, not an
oversight, but I'd want to hear a counterargument on the acceptable window.

## Database & Backend

**15. Why validate the migration with `pglast` instead of just running
`docker compose up` and seeing if it works?**
The development sandbox had no Docker daemon, so that verification path
wasn't available. Rather than assume the DDL was correct, I parsed it
with `pglast` (the real PostgreSQL grammar, used by Postgres tooling
itself) to catch syntax errors mechanically. It's a real substitute for
"does it apply cleanly," though it's not a full substitute for actually
running the migration against a live database — that's flagged as
outstanding user verification in `README.md`.

**16. Why raw hand-written DDL instead of Alembic autogenerate?**
Autogenerate infers migrations by diffing ORM models against the current
database state, which is convenient but can produce subtly wrong DDL
(missing indexes, wrong constraint names) that's easy to not notice.
Hand-writing the initial schema, then validating it independently, was
judged worth the extra effort for a schema this consequential.

**17. What happens if two requests hit `increment_failed_login` at the
same time?**
It's implemented as `UPDATE ... RETURNING`, a single atomic database
statement — Postgres serializes concurrent updates to the same row, so
there's no read-modify-write race. This fixed a real bug (see Q19) where
an earlier version read-then-wrote in Python instead.

**18. Why does `get_current_user` re-query the database on every
request instead of trusting the JWT's role claim?**
The claim was correct when the token was issued but can go stale (a
demoted or deactivated user). Re-checking `is_active` from the database on
every request closes that gap at the cost of one extra query — an
explicit trade-off against the alternative (trust the claim for the
token's full TTL), documented in `docs/subsystems/auth/DESIGN_DECISIONS.md`.

## Testing & Quality

**19. Walk me through a real bug your tests caught.**
An off-by-one in account lockout: the original `increment_failed_login`
mutated an object the caller had already read, then the service re-read a
possibly-stale copy, double-counting one failed attempt in some paths —
locking accounts one attempt early. Caught by a unit test asserting the
exact lockout threshold, fixed by making the repository method return the
authoritative post-increment count directly. Full writeup in
`docs/subsystems/auth/COMMON_FAILURES.md`.

**20. What's your test strategy — why unit AND integration tests for
auth?**
Unit tests (in-memory fakes) verify business logic in isolation, fast,
without a database. Integration tests (real FastAPI app via
`ASGITransport`, `dependency_overrides`) verify the actual HTTP layer,
serialization, and dependency wiring — which is where the `/auth/me`
testability bug (Q22 below) actually lived, and a pure unit test on
`AuthService` alone wouldn't have caught it.

**21. How do you know your tests aren't just decorative — that they'd
actually fail on a real bug?**
Because they did, three separate times during development (lockout
off-by-one, a FastAPI 204-response assertion error, and a DI gap that
made `/auth/me` untestable without a real database). All three are
documented with root cause and fix in
`docs/subsystems/auth/COMMON_FAILURES.md` — the honest evidence a test
suite is doing real work is that it caught real defects, not that it's
green.

**22. Tell me about a bug that wasn't caught by any test.**
The dummy-hash timing mitigation: an early version used a hand-typed
string formatted to *look* like an Argon2 hash but wasn't produced by the
real KDF. `verify_password()` against a malformed hash fails at parsing,
near-instantly — defeating the entire timing-equalization purpose. No
functional test would catch this (the login still correctly returns
"invalid credentials" either way); it would need a timing-focused test,
which doesn't exist yet. Caught by code review, not automation — which is
itself the lesson I take from it.

## Research Design

**23. What's the actual research question?**
Whether adversarial context (a poisoned CTI report, a misleading
false-positive comment) measurably increases the rate at which an LLM
drafts a Sigma rule with an exploitable blind spot, compared to the same
model under clean conditions — and whether human review and an LLM-judge
catch the difference.

**24. What's the ground-truth circularity bug you found, in plain
terms?**
My first draft used the same automated verifier both to define "is this
rule actually sabotaged" (ground truth) and to score how well it performs
as a detector alongside human review (a peer defense). Using one
instrument for both roles is circular — you can't validate a measurement
against itself. The fix was separating the verifier's role (ground truth
only) from the defenses being evaluated (human review, LLM-as-judge)
cleanly, documented in `docs/RESEARCH_DESIGN.md` §1.

**25. How do you avoid p-hacking or cherry-picking results?**
Pre-registered falsifiable hypotheses with explicit falsification
conditions, decided before any experiment runs. Wilson score confidence
intervals (more honest than a normal approximation at small sample sizes)
and Holm-Bonferroni correction for the multiple comparisons across the
corpus × model × condition matrix. Failure metrics (e.g., an underpowered
sample) are explicitly distinguished from a hypothesis being falsified, so
a null result and a broken experiment don't get conflated under pressure
to report something positive.

**26. Why do the production platform and the research harness share
code instead of using a separate lab environment?**
Because the research question is about whether a *real* review process
catches sabotage — using a simplified lab harness instead of the actual
approval workflow would make the result about the lab harness, not about
detection engineering as it's actually practiced. The trade-off is that
the research track has a hard dependency on the production rule-approval
workflow (E2) being built for real first, which is explicit in
`docs/ROADMAP.md`'s dependency graph.

## Process & Release

**27. Why run a release audit before the first tag instead of just
shipping E0?**
Because "it works on my machine" and "it's ready for someone else to
clone and judge" are different bars, and conflating them is exactly the
kind of overclaiming this project tries hard to avoid elsewhere. The audit
found 6 real issues (unused dependencies, a missing frontend lockfile that
would have broken CI immediately, a Docker Compose service with an
unnecessary Redis dependency) — none catastrophic, all worth fixing before
anyone else looked at the repo.

**28. What couldn't you verify, and how do you handle that honestly?**
`docker compose up` end-to-end, because the development sandbox had no
Docker daemon. Rather than claim it works, `README.md` has an explicit
verification-status table naming exactly what was and wasn't confirmed,
and by what alternative method (e.g., DDL parsed against the real
PostgreSQL grammar instead of applied to a live database).

**29. How do you decide what goes in `FUTURE_WORK.md` versus just not
mentioning it?**
Anything a reasonable reviewer would expect and might assume exists
(rate limiting, MFA, password reset) gets named explicitly, even though
naming a gap feels like it invites criticism. The alternative — silence —
reads as either not having thought about it or hoping no one asks, both
worse than a direct answer.

**30. What's the single thing you'd want a reviewer to look at first?**
`docs/subsystems/auth/COMMON_FAILURES.md`. It's the most concrete evidence
that the testing and review process here is real — three actual bugs,
root-caused and fixed, not a hypothetical list of "best practices
followed."
